# Evaluate a diagnosis on TrustMem-Bench P3

Given one observed execution with a historical receipt removed, predict how a specified intervention would change the set of completed requests. The organizer builds the scoring archive with `python reproduce.py p3 --out native-p3` (which rebuilds the immutable 198-file P3 adjudication cohort originally sealed as RC6; typical CPU runtime is 30–50 minutes). A participant needs only the exported observations and their own predictor. The Python 3 standard library is sufficient.

## Run the example

Run the following commands from the benchmark root or the unpacked interface kit. The commands below use the organizer archive generated by the `1.0.0-rc7.3` recipe (allow ~30–50 minutes on CPU for step 1). Each command writes a new file. The organizer builds the archive, exports observations and scores predictions. Give the participant only the observations and predictor interface for the prediction step.

```sh
python reproduce.py p3 --out native-p3
python trustmem_bench/p3_submission.py export --archive native-p3/organizer-p3.zip --out cases.jsonl
python trustmem_bench/p3_submission.py run --cases cases.jsonl --predictor examples/p3_threshold.py --out predictions.jsonl
python trustmem_bench/p3_submission.py score --archive native-p3/organizer-p3.zip --predictions predictions.jsonl --out score.json
```

Export checks the pinned digest of the original loss-track file. It works even when that is the sole member of an organizer's input archive. Scoring additionally needs the pinned outcome and admission records. The participant runner sends one case on standard input to a fresh Python process in an empty working directory. The predictor returns one JSON object on standard output. For other languages, generate the same submission JSONL directly. The scorer reads data and never imports or runs participant code.

## Input and prediction contract

Each case has a stable `case_id`, a list of `questions`, and an `observation`. The observation includes the workflow, batch, controller mode, task, prices, targets, receipt scope, loss-arm dispatch decisions, native calls and responses, budget balances, and observed completed targets. It also carries the frozen diagnostic instrumentation for that arm, including the position and price of the designated same-value reread when observed. Separate branches, the full native grade, checkpoint metadata, sham identity, and frozen predictions are withheld from the export.

The observation has three distinct sources of information.

| Access | Fields and provenance |
|---|---|
| Participant, observed | Public task and prices, calls and tool responses, charges, balances, actual dispatch and the loss-arm completed IDs. |
| Participant, organizer annotations | `dispatch[].queue[].with_receipt_floor` uses the controller's quote function with the archived value temporarily restored when needed. Scope and same-value reread annotations use the registered key and historical reusable fields. Reproducing the export requires access to that archive and instrumentation. API Reliability T09 has an observed quote of 33 and a restored quote of 16 on its first queue. |
| Organizer, adjudication only | Native continuations for alternative interventions, their completed target sets and frozen grading references. These are held separately when the organizer administers the interface. |

Additional diagnostic fields present in each exported `observation` object (all computed strictly from the loss run and organizer annotations):
- `dispatch[].gates[]`: mid-target budget gates observed during the loss run (`needed`, `remaining`, `call_index`, `after_reject`, `lower_bound_only`).
- `focal_reread_different`, `focal_prior_rejected`, `focal_receipt_used_in_loss`: boolean flags describing whether the designated receipt drifted, was rejected, or was used in the loss run.
- `blocked_optional_post_publish_price`: price of an optional post-publication confirmation call blocked at budget exhaustion, when applicable.

| Question | Intervention relative to this same loss execution |
|---|---|
| `total` | Organizer places the exact archived value back before execution, then executes the batch. |
| `fee` | Leave the receipt absent and waive the designated same-value reread charge. The question is supplied when that observed charge exists. |

A predictor answers exactly the questions for its case. Each answer contains `label`, `added` and `displaced`. The two arrays contain distinct, disjoint original target IDs. List order has no significance. `added` means newly completed under intervention. `displaced` means completed only in the loss arm. The following is a synthetic example of a submission line for a case with one question.

```json
{"case_id":"example-T01-ordered","answers":{"total":{"label":"target_swap","added":["request-B"],"displaced":["request-A"]}}}
```

| Label | Meaning |
|---|---|
| `business_omission` | The intervention completes more requests. |
| `fewer_business_completions` | The intervention completes fewer requests. |
| `target_swap` | The total count stays equal and the completed set changes. |
| `confirmation_only` | The completed set stays equal and post-publication confirmation changes where observable. |
| `no_terminal_change` | The completed set and the measured confirmation outcome stay equal. |
| `undecided` | The predictor abstains. Supply two empty arrays. |

The submission must contain every eligible case exactly once. To reproduce the original D0 comparison, a determined class prediction may omit target identities. It can earn class credit, while exact credit requires the correct class and both directed sets. The scorer rejects malformed, missing or duplicate submissions. For a single-track comparison, make each prediction from that case alone. A fresh process provides input separation for cooperative predictors. For blinded administration, the organizer must control filesystem access to other cases and labels. Because the sealed P3 adjudication cohort (tagged `RC6` in scorer metadata) was published with this study, scores on these cases measure retrospective compatibility.

## Read the score

Evaluate `total` and `fee` separately. There are 128 eligible batch–controller pairs across five ReScopeBench histories. The 68 fee questions reuse a subset of these pairs. Report the all-five cohort and the four released workflows separately. The API Reliability workflow has upstream candidate status. Results include each workflow and each controller, including groups with zero eligible questions. Those groups have a null accuracy and coverage.

| Score field | Interpretation |
|---|---|
| `class_correct`, `exact_correct` | Number of correct classes and complete judgments. Exact accuracy uses all eligible questions in its group. |
| `coverage`, `abstained`, `decided_wrong` | Fraction with a definite answer, number of abstentions and wrong definite answers. |
| `exact_after_replaying_abstentions` | Exact answers if every abstention receives its sealed native answer. A wrong definite answer remains wrong. |
| `full_replay_calls`, `replay_calls_on_abstentions`, `replay_calls_saved` | Recorded additional native tool calls for replaying every applicable cell, replaying abstentions, and their difference. Predictor inference, original log collection and deployment overhead are outside this accounting. |

The supplied D1 uses the first unstarted target whose public entry price becomes affordable after the designated refund. Across the five histories it makes 46/128 exact judgments for `total` and 29/68 for `fee`, with full coverage. Report accuracy beside replay costs. For example, an always-decide policy incurs zero replay calls even when many decisions are wrong.
