# Ordinary calculation: availability, execution and completion are separate

2026-11-13. Development diagnostic over **all12 actual first-reader payloads** from the Mem0/verbatim pilot. No notes were rewritten or retrieved again. Every initial payload was copied byte-for-byte; independent per-branch tool caches restore only observations from the original same-backend earlier sessions. It is not a new longitudinal policy run or12 independent histories.

## Primary paired intervention

Both arms take fresh first responses. Control retains the original query/submit/abstain interface. The availability arm additionally permits `quality_check`, a public exact-arithmetic utility. It accepts model-supplied selected counts and a rational threshold; it cannot read sources, notes or hidden references, and does not validate that supplied numbers match them. Two action slots and legal query/cache access are common. State and within-state arm order were frozen and randomized.

The availability arm **never selected the calculator**. Its one paired improvement used an additional source-bound cache query; there was also another query without a changed correctness outcome. The counts do not demonstrate arithmetic-tool execution gains. Added instructions/transport tokens and response variation remain part of this availability intervention.

The original pilot's first outputs were not reused as the fresh control. Some identical observed states yielded changed responses, so an old error is not automatically stable. No outcome-based subset was selected and no model response was retried for a better answer.

## Separately frozen instructed-use control

After calculator nonselection was observed, a new ordinary policy instructed first-action calculation when visible evidence suffices, otherwise query, then second-action submission. All12 states were included again. It is an adaptive development reference, not a randomized causal contrast with the earlier round. Direct submissions would remain committed rather than being blocked or repaired.

It produced **9 correct submissions,0 wrong submissions,3 unfinished**. There were9 calculator invocations and6 queries, with770 source-read bytes across restored branches. All12 followed the first-tool instruction. Three query→calculator sequences used the final action for a second tool, despite the instruction to submit, so no delivery existed when the budget ended.

The12/12 first-tool count checks only that an initial tool was chosen; it is not full-policy compliance. Two90% states already had a sufficient marginal bound75/80, but queried anyway. The new-source99% case did need a query. Thus unfinished outcomes also involve tool-choice and terminal-action policy compliance, not an intrinsic need for more than two actions in every case.

Two unfinished cases had a final correct calculator value but no submitted answer. In `verbatim-s03`, the reader supplied80/100, although the current tool's selected population was80 and the valid share was80/80. The calculator correctly returned0 for the supplied0.8 share against0.99; the task's actual answer was1. That is an intermediate parameter-binding error, not a wrong committed action or arithmetic-kernel defect. Numeric agreement with a hidden reference is also not proof of correct evidence binding.

The zero-wrong-submission count is not a free safety gain: legal completion remains9/12. These observations motivate a useful benchmark diagnosis separating **tool availability, chosen action, task-to-parameter mapping, executed result and final commit**. No new memory mechanism is claimed.

## What this adds to TrustMem-Bench

This is a stronger ordinary baseline and a reproducible process-diagnostic case, rather than an author algorithm. The optional-tool result prevents claiming improvements for tools that never executed. The instructed-policy result prevents claiming safety from unfinished tasks or counting a correct intermediate tool result as a completed task. The wrong denominator exposes a stage that end accuracy alone cannot localize.

Next engineering work should expose tool traces, remaining action slots and task parameters consistently across native adapters, retain the independent terminal outcome, and validate controls with both adequate and inadequate notes. New budget/tool-layout interventions need separate frozen protocols; the current two-action results stay unchanged. More calls to the same states are not independent confirmation.
